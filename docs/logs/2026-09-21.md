## Decisions
- Considered and declined a direct "run the coding agent from a terminal-style UI" bypass on the Scaffolded Files page - it would duplicate the Orchestrator's approval/audit/run-tracking machinery as a second, un-audited path to the same consequential action. Kept the single path: a shortcut button that opens the Orchestrator chat pre-filled, same gate as always.
- QA/Tester scope: Playwright only (no Robot Framework) - it already covers both UI and API testing via its `request` fixture, and Robot Framework would add a whole separate Python runtime with zero existing footprint.
- Deployer is plan-only by design (release notes/change/rollback plan for a human to execute) - there is no real deployment pipeline in this repo, so it must never claim a release happened.
- Git workspace tool runs directly on the host, not sandboxed - `node:22-slim` has no git installed anyway, and the target directory is already host-trusted (Dev/Code gates already write into it directly).

## Blockers / open questions
- `mastra api tool execute`'s CLI has its own short default request timeout (30s), far shorter than a real scaffold/coding Docker run. Firing a second `execute` call against the same draftId before the first one (still running server-side) finishes raced on the Docker container name and corrupted the draft's `filed` status - caught and manually corrected once during KAN-36 testing (`aura-drafts.db` row for `DEV-16ef5f52`). The execute path has no lock against concurrent calls on the same in-flight draftId; worth adding if this CLI-driven testing pattern continues.
- Direct `mastra api tool execute` calls against agent-runtime (used throughout today's live testing and the KAN-36 run) do **not** create `run_steps`/`approval_requests`/`audit_logs` rows in `apps/api` - only real traffic through `apps/api`'s own endpoints (the actual web app) is audited. The governance/audit trail described in `docs/ARCHITECTURE.md` section 4 only exists for that path.
- 4 of KAN-36's 9 Tasks (KAN-42 Data, KAN-44/KAN-49 Integration, KAN-50 Deployment) have no Gate 4 automation at all regardless of backend framework choice - they need manual implementation outside AURA.
