## 5. Architect Workflow rebuild

Rebuilt the Architect from one single-shot model call into a Mastra **Workflow**: requirements
analysis → system decomposition → {API, data, security, AI design} run in parallel → deployment
notes → ADRs and tasks. Each step is a narrow, separately-validated LLM call; the sequence is
decided by code, not a model — this was a deliberate choice over Mastra's native `subagents`
feature, which would let the model itself decide when to delegate.

The Orchestrator still sees exactly one tool, `delegate_to_architect` — the workflow runs inside
it. Each step's progress is relayed live into the same tool stream (a new `progress` kind on
`run_steps`), so the Run Console and live chat both show real per-section progress
("Security design — done") with no separate tracking system.

## 7. Four real bugs, found by actually running the system

Reading the code wasn't enough to catch these — they only showed up once the real pipeline was
driven end to end against the live runtime and Jira project:

1. **Jira's create-issue response was double-wrapped.** Mastra's MCP proxy sometimes returns
   `{result: "<the real JSON, still a string>"}` instead of the object itself. An Epic was
   actually created successfully but reported as failed. Fixed by unwrapping that extra layer.
2. **The real cause of "expected 'key' property to be a string".** The Jira parent-issue field was
   being sent pre-wrapped (`{key: epicKey}`), but mcp-atlassian wraps it itself — so it landed as
   `{key: {key: "KAN-3"}}`, which Jira's API correctly rejected. This affected every Story and Task
   filing attempt and had never been isolated before. Found by calling the MCP server directly and
   reading the Python traceback. Fixed by sending the bare key string.
3. **The Architect Workflow started with no `initialState`.** Mastra validates it against the
   workflow's full state schema before the run begins; only the input data was being passed, so
   every state field came back `undefined`. Fixed by seeding the initial state properly.
4. **`readdir('/')` fails under `LocalFilesystem`'s containment check** — a bare `/` is treated as
   escaping the workspace root rather than referring to it. Fixed by using `readdir('.')`.

With all of these fixed, the real pipeline ran end to end for the first time: BA drafted and filed
real Stories, and the Architect Workflow ran all its steps live (parallel steps genuinely
concurrent), got approved, and filed real Jira Tasks with real ADRs and design documents written
to disk.

  many fast file operations; path containment on every tool call is the safety boundary here, not
  a container — verified against eleven edge cases (including a same-name-prefix sibling directory

  sample file and a one-line task, it listed files, read the content, made exactly the requested

## Decisions

- Scoped "build the other agents" to the Architect only, for the morning session. **Superseded
  same day**: the Dev and Coding agents were built in the afternoon session once real
  infrastructure existed to build them against (Docker, per-user credentials) — see §15/§16. The
  "no faking results" principle held throughout: Dev agent claims are scoped exactly to what was
  verified (Frontend yes, Backend no), not to what was merely written.
- `qa_engineer`/`tester`/`deployer` roles exist and are assignable, but get no agent — there's
  nothing yet to grant them access to. (`developer` now does, as of the afternoon session.)
- Architecture tasks are filed under the Epic (not individual Stories) — Jira's parent field takes
  one parent, and each task's `relatedStories` field records what it actually implements.
- The agent manifest (`agents/registry.ts`) is enforced at startup, not just descriptive — the
  same kind of doc-vs-reality drift that caused the provenance-stamp and RLS corrections earlier
  today would otherwise happen again silently.
- A Mastra Workflow over Mastra's native `subagents` for the Architect's internal steps — code
  decides the sequence, not a model.
- The document workspace is read-only everywhere except the Architect's own approved `file` step —
  no agent or web page has a write path onto it. **Extended, not reversed**, in the afternoon
  session: a narrow architect-only manual-edit path was added (§13), still nowhere near as open as
  "no agent or web page has a write path" reads on its own now — see that section for the exact
  restriction.
- Sandbox isolation for Dev-agent code execution (open question below, and in
  `docs/ARCHITECTURE.md` §15 decision #4): resolved for this local/solo pass as Docker, one
  container per run — not Firecracker/gVisor, which only earns its complexity at multi-tenant
  scale.
- Coding-agent credentials live only in `apps/api` (Supabase + the encryption key);
  `apps/agent-runtime` fetches a decrypted key just-in-time over a new internal HTTP call rather
  than getting its own Supabase client — keeps the "apps/api owns identity" boundary from growing
  a second copy.
- The built-in Coding Agent's safety boundary is its tool surface (three tools, no shell), not a
  container — a real coding loop needs many fast file operations, and re-sandboxing every
  read/write in Docker would make that impractical. Claude Code/Codex, being full autonomous
  agents with their own broad tool systems, still run in Docker.
- Env secrets for this feature (`CREDENTIALS_ENCRYPTION_KEY`, `RUNTIME_INTERNAL_TOKEN`) were
  generated but not written into either `.env` file without being asked first — per earlier
  feedback that configuring env is a developer task, not something to do proactively. Both were
  set once the user explicitly asked for it.
